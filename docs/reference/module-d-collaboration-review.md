# 模块 D 协作稿审查与补充

审查日期：2026-10-15。基准：当前 C 首批服务机制、生成器 0.9.0。输入是用户提供的“模块 D：基于 NPC 性格差异的动态互动分支系统”粘贴文本。本次只审查与补充，没有合入其中的游戏代码和正文。

结论：结构化性格、纯查询、两阶段互动、免费退出的方向可保留；当前稿不能作为“可直接复制、已完整对齐”的交付。以下问题应在合并前解决。

## 必须修正的问题

### 1. 新系统没有接到正常 NPC 对话入口

当前 `src/world/generator.ts:136` 的交谈动作执行 `resident.talk`，不执行 `narrative.start`。`src/engine/entity-functions.ts` 把两种动作都归为 talk；`src/engine/selectors.ts:35` 的去重优先保留直接居民对话，因此在当前首批世界里，通用 `progression:action.narrative.conversation` 也被移除。

实际示例已验证：铁匠的正常交谈仍走短对话，选项中没有通用叙事对话入口。只增加 12 个节点不会让正常交谈进入它们。需明确短对话、深入交谈的产品行为和统一入口，调整相应去重规则；不要重新加出一组意义重复的按钮，也不能影响交易、工作和教学。

### 2. “跨包后加载所以不能校验”的判断不成立

`src/content/loader.ts:219` 先由全部包建立 Registry，再在 221 行执行 `validateDistrictDefinitions`。真正的问题是跨包依赖与可能出现的循环依赖，而非定义尚未加载。

不能因此把 traitTags 降为“格式正确即可”，再用 `has()` 静默丢弃错误 ID。应在完整注册表阶段验证：已注册、active、属于允许的性格集合、显式依赖正确。基础 district 不能反向依赖已经依赖它的 adventure；可把共享性格定义放在不依赖 district/adventure 的共同字典包，或把显式绑定放在已经能合法依赖两者的内容包。确定一种方案后更新构建与快照契约。

附件称 `progression:trait.*` 必然被 adventure-schema 拒绝也不准确：本次最小验证中，`progression:trait.review-proof` 与 `progression:tag.trait.review-proof` 都通过真实加载。`.tag.` 是现有构建辅助函数的命名约定，适合统一采用，但不是该 Schema 强制的子前缀。

### 3. 不能保证旧生成存档自动生效

`src/persistence/codec.ts:211` 从旧世界自身的 `world.definition.packs` 恢复 Registry。仅升级安装目录的 adventure 包，旧世界仍没有新性格 Tag 和节点。现有 `upgradeUXContent` 只处理精确已登记前身，不能当通用升级器使用。

已验证：用带新测试 Tag 的安装 Registry 读取当前首批示例，恢复的世界仍没有该新 Tag。须二选一并明确交付：仅新世界使用 D，旧档保持原行为；或编写针对已发布前身指纹的显式迁移。不得关闭哈希检查、重新随机生成 NPC，或宣称 undefined 兜底就能“新老档 100% 生效”。若改变生成输出，应更新生成器版本，并同步所有版本分支与旧档识别。

### 4. 绑定对象和在场规则没有闭环

附件的 `narrativeTags` 兜底会在任何故事里读取当前选中的居民，将其性格作为 opponent 注入；可能把路人的性格带进战败或别的故事。应限制到已绑定居民的 conversation，不从其他选中人物补对象。开始时锁定 `story.actor`，后续条件、正文、对话记忆和效果均使用同一对象。

当前 `resident.available` 和 `resident.talk` 读的是 currentResidentId，并非 story.actor。草稿也没有处理推进时间后 NPC 按日程离场的情况。应冻结规则：交谈期间是否暂留、离场后终止还是暂停。不得正文继续描写离场人物，而效果落到另一人身上。任何失效情形都要保留无资源退出。

### 5. 只检查 ID 格式不足以保证性格真实性

实例存档还需验证 traitTags 的来源、集合、范围和与模板的对应关系。附件允许任意注册 Tag 进入显式数组，随后注入 opponent；可能把身体或场景事实冒充为性格。尤其不能用它赋予未真实存在的身体语义。

文首说兼容两种前缀，给出的 resolveResidentTraitTags 却原样返回显式 ID，没有归一化逻辑。应在导入/迁移边界做明确且经过验证的映射，再检查重复，不能靠运行时过滤吞掉。

### 6. 分支后果与奖励尚未构成系统

多个负面选择仍进入相同 deepen 阶段，后续照常给正收益；这会把不同态度做成换一段文案后汇合。需明确 NPC 反应、拒绝/离开、信任变化及可继续条件。六类性格应是行为倾向，不能等同于一次选择后必然接受后续。

新增声望、影响、安全等奖励没有人物/阶段的持久领取限制。maxVisits 仅限制单次 story，重新开始会重置。最小中性节点已复现两次开启均获奖励。需要通过已登记的持久状态限制或调整奖励；重复查看与读档不能刷收益。

“赠送饮品或物件”的分支没有物品持有检查及消耗；“提供情报”“约定巡查”等没有对应的发现、任务或约定记录。若只是聊天话题，文案应如实表达；若承诺实际功能，必须提供真实效果，不能再制造一层叙事占位。

## 应补充的设计约束

1. **结构化数据优先。** 新 NPC 的性格应由已登记的模板/词库组合在创建时确定并保存。自由文本关键词仅用于明确的兼容适配；职业不能直接决定性格，未知文字也不应靠字符哈希强塞进六类之一。无匹配时走普通对话。“温和=虔诚”“安静=羞怯”并不可靠。
2. **性格不代替身体和场景。** 草稿正文默认有衣领、手套、双腿、墙面等，现有游戏包含不同 BodyGraph 和地点。涉及身体动作、衣着、器具或环境的内容必须有真实条件或适配文本，无条件节点应使用通用表达。
3. **偏好与人物意愿分别判断。** 当前 preference.adultOptional 只检查玩家创建与偏好，不代表对方同意或接触条件成立。可选分支应单独验证绑定人物的资格、在场状态和当前互动边界；关闭偏好后普通对话须完整、自然，不能自动进入同一亲密升级段落。
4. **权重规则明确。** 当前 nodeWeight 只从 profile.tendencies 和环境 Tag 给 tendencies 加权；仅把性格放在 opponent 不会产生附件宣称的倾向加成。requiresTags 的硬筛选仍有效，基础 weight 也有效。若需要多性格组合的软权重，应显式接入并同步调试解释，不要只填一个实际不参与计算的数值。
5. **多样性可验收。** 六类各两段是十二个固定模板，不等于丰富的程序化互动。应按性格、职业、关系阶段、当前话题和实际地点组合；先保证有限组合语义正确，再增加文本变体。没有候选时回退到已完成的普通内容，不能露出制作说明。
6. **保留当前 C 契约。** 不能整文件覆盖丢失 services、roleName、设施筛选、支持但缺资源的提示或不支持功能隐藏。不要把性格、职业和服务权限合成一个二元 functional 字段。
